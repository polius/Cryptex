# Cryptex crypto format v1

Status: **v1, in use** by Cryptex. A change to the format is a v2, told apart as §5 says; §6 is the checklist for anyone reviewing an implementation.
Normative companions: `api/tests/reference.py` (reference implementation) and `vectors.json` (test vectors it generates and verifies).
Every implementation (the browser worker, and any future client) must reproduce every value in `vectors.json` and reject every `must_fail` case, including the reveal checks of §3.4 (`cases.reveal`).

## 0. Goals and non-goals

- The server stores only ciphertext, sizes, times and hashes of high-entropy tokens. It never sees contents, file names, titles, sender names, link keys or passphrases.
- Holding a secret's ID authorizes nothing. Every operation needs a token derived from, or issued alongside, the link key.
- Chunked uploads and downloads resist tampering, truncation, reordering and extension.
- Non-goal: protecting against a malicious server operator who changes the JavaScript the server serves (see `threat-model.md`).

## 1. Notation

- `||` concatenation; `u32be(i)` 4-byte big-endian; strings are UTF-8.
- `b64u` is base64url without padding (RFC 4648 §5).
- `HKDF-Extract` and `HKDF-Expand` are RFC 5869 with SHA-256. `Expand(prk, label)` means `HKDF-Expand(prk, info = label, L = 32)`.
- `AES-GCM` is AES-256-GCM with a 96-bit nonce and a 128-bit tag; ciphertext output is `ciphertext || tag`.
- `random(n)` is `crypto.getRandomValues` (the browser), or the platform's cryptographically secure generator in any other client.

## 2. Identifiers

- Secret ID: 10 characters from `[0-9A-Za-z]` (base62), generated by the server, about 59 bits. It's a routing key, not a secret.
- Because every derived value is bound to the ID, a client creates the item first (policy and stream sizes only), receives the ID, then encrypts and sends the ID-bound values (`meta_ct`, `reveal_hash`, `passcheck_hash`) with **seal**.
- `salt(id) = "cryptex/v1/" || id`

## 3. Sending a secret

### 3.1 Link key and derived values

```
K            = random(16)
prk          = HKDF-Extract(salt(id), K)
content_key  = Expand(prk, "content")
meta_key     = Expand(prk, "meta")
reveal_token = Expand(prk, "reveal")
link         = https://{host}/s/{id}#{b64u(K)}         // fragment is exactly 22 characters
```

The client sends `reveal_hash = hex(SHA-256(reveal_token))` with seal. The token itself goes in `Authorization: Reveal {b64u(reveal_token)}` on the `meta`, `reveal` and `report` calls (`report` only on the demo server). Because the token has 256 bits of entropy, a fast hash is correct here; no salt or slow hash is needed.

A client that finds a fragment that isn't exactly 22 base64url characters must show the "link incomplete" screen without calling the server.

### 3.2 Passphrase (optional)

```
salt_pw      = random(16)                              // stored in clear in the secret's policy
pw           = Argon2id(passphrase, salt_pw, m = 47104 KiB, t = 1, p = 1, len = 32)
prk'         = HKDF-Extract(salt(id), K || pw)
content_key  = Expand(prk', "content")                 // replaces §3.1 content_key
passcheck    = Expand(prk', "passcheck")
```

- `meta_key` and `reveal_token` still come from §3.1, so the title shows before the passphrase is asked.
- The client sends `passcheck_hash = hex(SHA-256(passcheck))` with seal, and `X-Passcheck: b64u(passcheck)` with `reveal`.
- The server checks the passcheck **only after** the reveal token matches, counts failures, and destroys the secret after 5. Someone without the link can't burn it.
- Generated passphrases are 20 characters from an unambiguous 64-character alphabet with symbols (120 bits), like generated passwords. Nothing is filled in until the sender asks for one.

### 3.3 Metadata blob (title and sender name)

```
plaintext = JSON {"title": string|null, "from": null, "fields": int, "notes": int}   // counts let the sealed page say "3 fields and 1 file"
nonce     = random(12)
meta_ct   = b64u(nonce || AES-GCM(meta_key, nonce, plaintext, aad = "cryptex/v1|meta|" || id))
```

Maximum plaintext 1 KiB.

`from` is always `null` (decoders ignore it). A sender's name inside the encrypted metadata is whatever the sending
browser claims, so the sealed page never shows it: it shows the `sender` the server returns with the metadata, which
is the current username of the signed-in account that created the secret, or nothing for an anonymous sender.

### 3.4 Payload: STREAM over AES-GCM

A secret has one or more streams. Stream 0 is the manifest; stream `n ≥ 1` is the file the manifest points to.

```
manifest = {"v": 1, "items": [
  {"t": "note",  "v": string},
  {"t": "field", "k": string, "v": string, "secret": bool},
  {"t": "file",  "name": string, "type": string, "size": int, "stream": int}
]}
```

For every stream:

```
prefix   = random(7)                                   // sent in the stream descriptor on create
aad      = "cryptex/v1|" || id || "|" || u32be(stream)
nonce_i  = prefix || u32be(i) || last_flag             // last_flag = 0x01 on the final chunk, else 0x00
chunk_i  = AES-GCM(content_key, nonce_i, plaintext_i, aad)
```

- Encoders split plaintext into 5 MiB pieces (5,242,880 bytes); only the last may be shorter. An empty stream is one empty chunk with the last flag set.
- Decoders accept any chunk up to 5 MiB + 16 bytes and must fail if: any tag fails; the final chunk lacks the last flag (truncation); a non-final chunk has it (extension); chunks are out of order; a chunk is decrypted under another stream index; or the chunk list is empty (a stream always has at least one chunk).
- Each chunk is authenticated, but only the server's stream list says which streams exist. On reveal, decoders must also fail if:
  - the stream list isn't exactly `0 … n−1`, each number once, each stream with at least one chunk, a size and a 7-byte nonce prefix (stream numbers, chunk counts and sizes are integers; the prefix is 10 base64url characters);
  - the manifest isn't a JSON object with an `items` array of objects (items with another `t` are ignored, for later versions of v1);
  - a `file` item's `stream` isn't an integer, or points to stream 0, to a stream that isn't in the list, or to a stream another item already uses, or a stream `n ≥ 1` isn't used by any item;
  - a file's decrypted size differs from the manifest's `size`.

  Together these stop a server from dropping a file, emptying it, or swapping two files' contents under the right names. Nothing is shown, and the read isn't confirmed, until every check passes.
- Chunk count per stream is limited to 2³² − 1 by the counter (far beyond any configured file limit).

### 3.5 Tokens issued by the server

- `upload_token`, `manage_token`: `random(32)` on the server, returned once on create, stored as SHA-256.
- The upload token dies when the secret is sealed or after 30 minutes without activity.

## 4. Asking for a secret

Someone makes a request link; whoever opens it sends them a secret, with or without an account. The answer is an ordinary secret (§3) whose link key only the requester can read.

### 4.1 The request

```
R             = random(16)                             // the request link's key
prk           = HKDF-Extract("cryptex/v1/ask/" || id, R)
ask_key       = Expand(prk, "ask")
answer_token  = Expand(prk, "answer")
link          = https://{host}/a/{id}#{b64u(R)}         // fragment is exactly 22 characters
(d, Q)        = ECDH P-256 key pair, made by the requester's browser; d is kept with the request (account vault, or
                this browser without an account)
ask_ct        = b64u(nonce || AES-GCM(ask_key, nonce, JSON {"key": b64u(Q), "note"?: text}, aad = "cryptex/v1|ask|" || id))
```

- `Q` is the 65-byte uncompressed point. It travels inside `ask_ct`, so the server, which never sees `R`, can't swap it for a key of its own.
- `note` is optional: what the requester wrote for whoever answers (who they are, what they need), at most 1000 characters. Anyone with the link can read it; the server can't. It is shown as plain text, as the requester's own words.
- The requester creates the request (the server assigns `id` and a manage token, §3.5), then seals it with `ask_ct` and `answer_hash = hex(SHA-256(answer_token))`.
- Whoever holds the link sends `Authorization: Answer {b64u(answer_token)}` to read `ask_ct` and to start the answer. The link can't read the answer.

### 4.2 The answer

The answer is a secret (§3) with its own ID `sid` and link key `K`. Its key is encrypted to `Q`:

```
(e, E)        = a new ECDH P-256 key pair, used once
z             = ECDH(e, Q)                              // 32 bytes
prk_a         = HKDF-Extract("cryptex/v1/answer/" || id || "/" || sid, z || E || Q)
wrap_key      = Expand(prk_a, "answer")
answer_ct     = b64u(E || nonce || AES-GCM(wrap_key, nonce, K, aad = "cryptex/v1|answer|" || id || "|" || sid))
```

`answer_ct` goes with the answer's seal. The requester computes `z = ECDH(d, E)`, gets `K`, and opens `/s/{sid}#{b64u(K)}` like any link. A request takes one answer: the first one sealed. The answer expires with the request.

## 5. Versioning

- The version string appears in every salt and AAD. A future v2 changes the route prefix (`/s2/`) and the string, so formats can never be confused.
- The manifest carries `"v": 1` for content-level changes inside v1.

## 6. Review checklist (for anyone reviewing an implementation)

- [ ] Nonce uniqueness: one random prefix per stream per secret; counters never repeat inside a stream.
- [ ] Key separation: distinct HKDF labels for every purpose; IDs bound in salt and AAD.
- [ ] Truncation, extension and an empty chunk list rejected (`must_fail` cases).
- [ ] Stream list and manifest checked against each other on reveal (§3.4): no missing, extra, reused or resized file (`reveal` must_fail cases).
- [ ] Passphrase failures can't be triggered without the link key.
- [ ] No secret material in logs, URLs other than fragments, or error messages.
- [ ] A request's public key is taken only from inside `ask_ct` (§4.1), never from the server in the clear.
