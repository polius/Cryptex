# Threat model

## Assets

1. Secret contents (notes, fields, files) and their titles and sender names.
2. Link keys (URL fragments) and passphrases.
3. Capability tokens (reveal, upload, manage, read sessions) and sessions.
4. Metadata: who sent what to whom, and when.
5. Availability of the service and its disk.

## Adversaries and what they get

| Adversary | Can | Can't | Mitigations |
|---|---|---|---|
| Stranger on the internet | Guess IDs, send requests, fill the disk | Read, burn, destroy or add to any item (needs tokens); fill the disk past `MIN_FREE_DISK` | Capability tokens, uniform 404, per-IP limits incl. IPv6 /64 (create, chunk uploads, receipt lookups), failed-token blocking (also for wrong manage tokens in lookups), disk-space guard, no orphaned uploads |
| Someone who sees a link in transit (chat history, forwarded email) | Reveal it if it's still unopened (or not one-time) and has no passphrase | Reveal it without the passphrase; reveal a one-time link after it was opened; stay unnoticed | Passphrase (sent another way), one-time links (an option), sender sees “Opened” immediately with the time |
| Someone who sees a request link (“Ask for a secret”) | Send the one answer before the intended person does | Read the answer (its key is encrypted to the requester's public key, kept with the request: their vault, or their browser); swap that public key (it's sealed with the link's key); answer twice | One answer per request, first sealed wins; the requester sees when it came in, and asks again if it wasn't expected. The page never names who asks (a username is half of a sign-in): it shows the requester's optional note, encrypted with the link (their own words, which nobody checks), and a short code made from the request's ID that the requester sees too |
| Link scanners and previews | Load the sealed page | Consume the secret | Nothing changes on load; reveal is a POST after a click |
| Recipient's device later | Read the browser history | Recover a revealed secret | Fragment removed from the URL bar, page auto-clears, nothing stored |
| Thief of the database file alone (without `enc.key`) | Read all tables and chunks: counts, times, usernames, token hashes, ciphertext | Decrypt anything; read Your links; test password guesses offline (the password verifier is argon2id of an HMAC keyed with `ENC_KEY`, and so is a temporary password's hash); read 2FA secrets, unlock shares or device keys; try reset codes offline (keyed hash) | E2E format, token hashes only, vault items encrypted in the browser, everything server-side secret sealed or keyed with the server key (`ENC_KEY`), which is a separate file, `enc.key`. It sits in the same data folder and backups, so a thief of the whole folder or a backup is the next row |
| Thief of the data folder or a backup (database + `enc.key`) | Guess account passwords offline, one Argon2id in the browser's settings (64 MiB, 3 passes) plus one on the server's (19 MiB, 2 passes) per guess; read every 2FA secret, so 2FA no longer stands in their way for an account whose password they guess; read device keys | Read link contents or titles (they never reach the server unencrypted); read Your links of an account whose password they don't guess (the vault key is wrapped by the password and the unlock share) | 8-character minimum and the two Argon2id passes make each guess slow. **Weak passwords remain the residual risk**, larger with 8 characters than with 12; 2FA doesn't help against this thief. Keep the data folder and its backups as private as the server. |
| A phishing page that captures a password | Know the password | Sign in without the 2FA code, even from many addresses | 2FA, for people who turn it on (optional, recommended at invite and after setup); 5 codes per sign-in ticket, counted atomically; 30 wrong codes and passwords per account per hour from anywhere, reserved before each check so parallel requests can't exceed it, then none are checked; a code works once, even for two requests racing with it. **Accounts without it fall to a phished password.** |
| Online password guesser (many addresses, or a spoofed `X-Forwarded-For` behind a misconfigured proxy) | Try passwords against the sign-in form | Try more than 30 an hour per account, whatever the addresses; more than `RATE_AUTH` per address | Per-account limit (30 wrong passwords and 2FA codes an hour, counted per username so unknown names answer the same), per-address `RATE_AUTH`, both reserved before the work; `TRUSTED_PROXIES` names exactly the proxy and the log warns about private client addresses. **The per-account limit lets someone lock a known username out of signing in for an hour**: a deliberate trade for bounding guesses. |
| Someone who asks for another person's temporary password | Make the server write one (“Forgot your password?” takes only a username) | Read it; lock the person out; replace one already passed on; learn whether the account exists (from the answer or its timing); use one after the account's password changed | The password is only in `DATA_DIR/temp-passwords`, readable by whoever runs the server; the old password keeps working; one waiting isn't replaced; same answer and timing for unknown usernames (its key is derived after the response, and sign-in compares a hash, no server-side Argon2); bound to the account's current salt and voided by any credential change (password change, invite, owner reset, reset link, removal); per-IP limits; audit events. **It skips the 2FA code and turns 2FA off (it is also the way back from a lost authenticator), so whoever passes it on must check who is asking. Until used or 24 hours pass, it sits in plain text in the data volume and its backups.** |
| An owner who wants into someone else's account | Make a reset link and code for them and use both | Do it unnoticed; read the person's saved links | Audit event; the person is told at their next sign-in (and can cancel a pending link); once used, their old password stops working. Saved link titles and copies are deleted by the reset, never handed over. **Owners are trusted with accounts, not with content.** |
| Someone who sees a reset link in chat history | Open the reset page | Use it without the code | Separate 8-character code (40 bits) meant for another channel, keyed hash only, 5 wrong codes end the link, 24-hour expiry, one use |
| Curious server owner | See counts, sizes, times, signed-in senders' usernames, audit log | Read contents or titles; reveal or destroy others' items | No admin bypass in the API; events hold no content |
| Malicious server operator (changes the code) | Serve JavaScript that leaks keys | Affect past secrets | Strict CSP, no third-party code, published release digests and build provenance (a `SHA256SUMS` release asset for the web files with a build-provenance attestation, and an SBOM and provenance for the image). **Residual risk, stated in the privacy notice.** |
| Abuser of a public instance | Host files or phishing for an hour | Keep content up, use it at scale; pass as someone the server knows | Demo limits (1 hour, a daily quota), proof of work, reports, breakers; recipients see only the sender name the server attests (a signed-in sender's username, and only when they are signed in here too; others see the organization's name), never the name the sender's browser wrote |
| Sender's stolen or shared computer, signed out | Copy the browser's storage | Read Your links (its copy of the vault key is locked with a device key only a session can fetch) | Device key gated by session; sign-out deletes the copy and the device key; “This is a shared computer” keeps nothing and is remembered by the server, whose session for it lasts 12 hours with a browser-session cookie |
| Sender's laptop while still signed in | See Your links; use the session | Open links already opened or expired; fetch what guessing the password offline needs; rewrap the vault; start a new 2FA enrolment | Link keys deleted at final status; the unlock share and `vault_pw` only after the password (POST /me/vault/unlock); writing `vault_pw`, and every 2FA change including starting one, needs the password (re-auth); sessions end 14 days after last use and 30 days after sign-in at most; sign out remotely by changing the password. Other tabs and devices notice an ended session at their next request (`X-Cryptex-User`: 401 `ended`), never acting on as a visitor |
| Next person to sign in on a computer someone left signed in | Sign in to their own account over it | Keep the earlier account's session running behind theirs | Each sign-in ends the session the browser presented; the earlier account's other devices stay signed in |
| Not-signed-in sender's computer | See this browser's Your links | Open links already opened or expired | Link keys deleted at final status; clearing the browser’s site data removes the rest |
| Another device of an account after a vault reset or a password reset | Keep its copy of the old vault key | Open the vault with it again | A vault reset, and any reset that drops the password's wrapping of the vault key (temporary password, reset link, owner reset), deletes every device key of the account |
| Wrong or missing `enc.key` after a restore or redeploy | Start the server with another key | Silently break 2FA, vaults and device keys, or overwrite data with a new key | A canary sealed with the key at first start: another key refuses to start; no key is generated for a server that already has accounts |
| Someone behind the same proxy as everyone else | Share one rate-limit address with every visitor | Lock everyone out with a few wrong tokens or sign-ins | uvicorn takes the client address from `X-Forwarded-For` only from `TRUSTED_PROXIES` (private ranges by default; the port is published on 127.0.0.1 only); sign-in limits count failures, not attempts |

## Out of scope

Compromised recipient or sender devices (malware, keyloggers); recipients who copy a secret elsewhere after revealing it; traffic analysis by a network observer; denial of service beyond rate limits and breakers.

## Security requirements traced to tests

Every row above has at least one test in `api/tests/test_security.py` or the Playwright suite, named after the row, for example `test_stranger_cannot_destroy_by_id` and `e2e_scanner_load_does_not_consume`.
