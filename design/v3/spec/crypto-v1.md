# Cryptex crypto format v1

Status: **draft for independent review** (gate before CX-11 merges).
Normative companions: `reference.py` (reference implementation) and `vectors.json` (test vectors it generates and verifies).
Every implementation (browser worker, Go CLI) must reproduce every value in `vectors.json` and reject every `must_fail` case.

## 0. Goals and non-goals

- The server stores only ciphertext, sizes, times and hashes of high-entropy tokens. It never sees contents, file names, titles, sender names, link keys or passphrases.
- Holding a secret's ID authorizes nothing. Every operation needs a token derived from, or issued alongside, the link key.
- Chunked uploads and downloads resist tampering, truncation, reordering and extension.
- Non-goal: protecting against a malicious server operator who changes the JavaScript the server serves (see `threat-model.md`). The CLI removes this for API users.

## 1. Notation

- `||` concatenation; `u32be(i)` 4-byte big-endian; strings are UTF-8.
- `b64u` is base64url without padding (RFC 4648 §5).
- `HKDF-Extract` and `HKDF-Expand` are RFC 5869 with SHA-256. `Expand(prk, label)` means `HKDF-Expand(prk, info = label, L = 32)`.
- `AES-GCM` is AES-256-GCM with a 96-bit nonce and a 128-bit tag; ciphertext output is `ciphertext || tag`.
- `random(n)` is `crypto.getRandomValues` (browser) or `crypto/rand` (Go).

## 2. Identifiers

- Secret ID: 10 characters from `[0-9A-Za-z]` (base62), generated by the server, about 59 bits. It's a routing key, not a secret.
- Because every derived value is bound to the ID, a client creates the item first (policy and stream sizes only), receives the ID, then encrypts and sends the ID-bound values (`meta_ct`, `reveal_hash`, `passcheck_hash`, or `prompt_ct`, `answer_token_hash`) with **seal**.
- Request ID: same format.
- `salt(id) = "cryptex/v1/" || id`

## 3. Sending a secret

### 3.1 Link key and derived values

```
K            = random(16)
prk          = HKDF-Extract(salt(id), K)
content_key  = Expand(prk, "content")
meta_key     = Expand(prk, "meta")
reveal_token = Expand(prk, "reveal")
link         = https://{host}/s/{id}#{b64u(K)}         // fragment is exactly 22 characters
```

The client sends `reveal_hash = hex(SHA-256(reveal_token))` with seal. The token itself goes in `Authorization: Reveal {b64u(reveal_token)}` on `meta`, `reveal` and `verify` calls. Because the token has 256 bits of entropy, a fast hash is correct here; no salt or slow hash is needed.

A client that finds a fragment that isn't exactly 22 base64url characters must show the "link incomplete" screen without calling the server.

### 3.2 Passphrase (optional)

```
salt_pw      = random(16)                              // stored in clear in the secret's policy
pw           = Argon2id(passphrase, salt_pw, m = 47104 KiB, t = 1, p = 1, len = 32)
prk'         = HKDF-Extract(salt(id), K || pw)
content_key  = Expand(prk', "content")                 // replaces §3.1 content_key
passcheck    = Expand(prk', "passcheck")
```

- `meta_key` and `reveal_token` still come from §3.1, so the title shows before the passphrase is asked.
- The client sends `passcheck_hash = hex(SHA-256(passcheck))` with seal, and `X-Passcheck: b64u(passcheck)` with `reveal`.
- The server checks the passcheck **only after** the reveal token matches, counts failures, and destroys the secret after 5. Someone without the link can't burn it.
- Generated passphrases are 4 words from the EFF large wordlist plus a 2-digit number (about 54 bits).

### 3.3 Metadata blob (title and sender name)

```
plaintext = JSON {"title": string|null, "from": string|null}
nonce     = random(12)
meta_ct   = b64u(nonce || AES-GCM(meta_key, nonce, plaintext, aad = "cryptex/v1|meta|" || id))
```

Maximum plaintext 1 KiB.

### 3.4 Payload: STREAM over AES-GCM

A secret has one or more streams. Stream 0 is the manifest; stream `n ≥ 1` is the file the manifest points to.

```
manifest = {"v": 1, "items": [
  {"t": "note",  "v": string},
  {"t": "field", "k": string, "v": string, "secret": bool},
  {"t": "file",  "name": string, "type": string, "size": int, "stream": int}
]}
```

For every stream:

```
prefix   = random(7)                                   // sent in the stream descriptor on create
aad      = "cryptex/v1|" || id || "|" || u32be(stream)
nonce_i  = prefix || u32be(i) || last_flag             // last_flag = 0x01 on the final chunk, else 0x00
chunk_i  = AES-GCM(content_key, nonce_i, plaintext_i, aad)
```

- Encoders split plaintext into 5 MiB pieces (5,242,880 bytes); only the last may be shorter. An empty stream is one empty chunk with the last flag set.
- Decoders accept any chunk up to 5 MiB + 16 bytes and must fail if: any tag fails; the final chunk lacks the last flag (truncation); a non-final chunk has it (extension); chunks are out of order; or a chunk is decrypted under another stream index.
- Chunk count per stream is limited to 2³² − 1 by the counter (far beyond any configured file limit).

### 3.5 Tokens issued by the server

- `upload_token`, `manage_token`: `random(32)` on the server, returned once on create, stored as SHA-256.
- The upload token dies when the secret is sealed or after 30 minutes without activity.

## 4. Requests

```
(priv, pub)   = ECDH P-256 key pair, generated in the requester's browser
P             = random(16)
fp            = SHA-256(SPKI-DER(pub))[0..8]
link          = https://{host}/q/{id}#{b64u(P || fp)}  // fragment is exactly 32 characters
prk_q         = HKDF-Extract(salt(id), P)
prompt_key    = Expand(prk_q, "prompt")
answer_token  = Expand(prk_q, "answer-token")
prompt_ct     = b64u(nonce || AES-GCM(prompt_key, nonce, prompt_json, aad = "cryptex/v1|prompt|" || id))
prompt_json   = {"title", "from", "message", "fields": [string], "files": bool}
```

The server stores `pub` (SPKI DER) from create, then `prompt_ct` and `answer_token_hash` from seal.

Answering:

1. Fetch `pub` and `prompt_ct` with `Authorization: Answer {b64u(answer_token)}`.
2. Check `SHA-256(SPKI(pub))[0..8] == fp`. On mismatch, refuse to encrypt and show an error: the server may have swapped the key.
3. Generate an ephemeral pair `(e, E)`. `shared = ECDH(e, pub)`; `answer_key = Expand(HKDF-Extract(salt(id), shared), "answer")`.
4. Encrypt the answer manifest and files with STREAM (§3.4) under `answer_key`, and upload `E` (SPKI DER) with it.

Reading: the requester computes `ECDH(priv, E)` and derives the same `answer_key`.

Key storage: generate `priv` extractable, export PKCS#8 once for the optional backup link (`/q/{id}/key#{b64u(pkcs8)}`), then re-import as non-extractable into IndexedDB. Account sync of private keys is out of scope for 3.0.

## 5. Versioning

- The version string appears in every salt and AAD. A future v2 changes the route prefix (`/s2/`) and the string, so formats can never be confused.
- The manifest carries `"v": 1` for content-level changes inside v1.

## 6. Review checklist (for the independent reviewer)

- [ ] Nonce uniqueness: one random prefix per stream per secret; counters never repeat inside a stream.
- [ ] Key separation: distinct HKDF labels for every purpose; IDs bound in salt and AAD.
- [ ] Truncation and extension rejected (`must_fail` cases).
- [ ] Passphrase failures can't be triggered without the link key.
- [ ] Request key substitution detected by the fingerprint.
- [ ] No secret material in logs, URLs other than fragments, or error messages.
